# Tauri 2 macOS Apple Silicon feasibility

## Scope and evidence boundary

**Superseded decision:** the user subsequently approved removing application-managed proxy support entirely. Retain Tauri/WKWebView and normal system-inherited networking; private-PAC and CEF experiments are cancelled. Proxy findings below are historical evidence, not outstanding requirements.

This report assesses the pinned Yangertron behavior on Apple-Silicon macOS; requirements are mapped in the [source inventory](yangertron-feature-inventory.md), commit `c6df711b3acff9b4e6208197de93a34c9fc9da13`. The original public-API assessment below is historical. Later native checks and the proxy blocker are recorded in the [implementation spec](../../implementation-artifacts/spec-telesram-desktop-app.md). The application opened the anonymous Messenger endpoint, which now advertises Telemost; no Yandex authentication or real call was performed. Comparative resource savings remain unmeasured.

**Status legend:**

- **Supported** — the cited public API directly covers the platform behavior.
- **Conditional** — the API exists, but has a version, configuration, permission, or site-behavior dependency.
- **Unverified** — public sources do not establish the requested end-to-end behavior; target-runtime validation is required.
- **Builtin gap** — the current public Tauri/Wry API does not expose the requested capability. This is not a claim that a custom native solution is impossible.

## macOS minimums and public-API constraints

- **General Tauri macOS floor is documentation-dependent:** the current [prerequisites](https://v2.tauri.app/start/prerequisites/) name Catalina **10.15+**, while the [macOS bundle guide](https://v2.tauri.app/distribute/macos-application-bundle/) says generated bundles default to **10.13+**. Treat 10.15+ as the current setup baseline; neither statement makes the requested feature set available below its individual API minimums.
- **Apple Silicon build target:** `aarch64-apple-darwin` ([Tauri signing guide](https://v2.tauri.app/distribute/sign/macos/)). The target is evidence of build targeting, not evidence that each requested browser feature behaves identically on every Apple-Silicon macOS release.
- **Persistent identified WebKit data store:** macOS **14.0+** ([Apple](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:))). Default persistent WebKit storage has a different, older availability story and is appropriate only as ordinary browser-session storage evidence.
- **Wry proxy support on macOS:** macOS **14.0+** plus the `mac-proxy` feature ([Wry builder source](https://raw.githubusercontent.com/tauri-apps/wry/d8fe88dc7be2f6ff00c671f823e985335a14f7ad/src/lib.rs)).
- **Camera/microphone delegate control:** macOS **12.0+** ([Apple](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:requestmediacapturepermissionfor:initiatedbyframe:type:decisionhandler:))). Camera/microphone authorization is separately required by macOS ([Apple](https://developer.apple.com/documentation/bundleresources/requesting-authorization-for-media-capture-on-macos)).
- **Native ScreenCaptureKit:** macOS **12.3+** ([Apple](https://developer.apple.com/documentation/screencapturekit)); this is not proof of WKWebView `getDisplayMedia` integration.
- **macOS menu shape:** menu items must be in submenus; macOS treats the first submenu as the app menu ([Tauri](https://v2.tauri.app/learn/window-menu/)).
- **Remote frontend trust:** remote origins need explicitly declared Tauri capabilities before they can invoke Tauri APIs ([Tauri](https://v2.tauri.app/security/capabilities/)). This matters for any injected unread-counter bridge, not for ordinary page rendering.
- **System-WebKit dependency:** Tauri uses WKWebView on macOS, and WebKit capability/version follows the installed macOS and its updates ([Tauri WebView versions](https://v2.tauri.app/reference/webview-versions/)). Every remote-page behavior claim therefore needs the target macOS version recorded during runtime validation.

## Original highest-risk compatibility boundaries

1. **Local screen capture works; messenger integration remains open.** The [runtime probe](screen-sharing-probe.md) produced usable window and monitor streams without a custom bridge. The next relevant check is the real site's WebRTC call path, not re-proving basic local capture.
2. **The requested full proxy behavior is not represented in Wry’s public type.** Current source covers only endpoint host/port for HTTP CONNECT and SOCKS5, with macOS 14+ feature gating. Authenticated proxies and bypass lists are builtin gaps.
3. **Robust analytics request blocking for remote Yandex traffic is not available through Tauri’s documented request hook.** Its hook is limited to `tauri:` protocol resources, so a wrapper must not represent it as an available Tauri 2 behavior.
4. **Remote-page customization has a security boundary.** Script injection is available, but granting a mutable remote origin access to native IPC requires explicit, narrowly scoped capability configuration. The actual unread indicator and CSS selectors are page-contract risks.
5. **Media capture raises the practical baseline above either documented general Tauri floor.** Camera/mic permission delegation is documented at macOS 12; proxies and identified profiles at macOS 14; native screen capture at 12.3.

## Measurement boundary for the RAM and size objective

No threshold is justified until an equivalent baseline is captured. A valid comparison should use the same Apple-Silicon hardware and macOS version, the same Yandex account/chat state or repeatable fixture, the same window count and dimensions, comparable network/proxy state, and defined cold-start and settled-idle points.

For memory, collect a time series and compare medians/percentiles of the **total attributed live process set**, not only the visible app parent: include the app and every WebKit renderer/network/GPU/helper process that the operating system attributes to the app at each sample. Record process membership with each sample so a helper-process difference is visible rather than silently excluded.

For artifact size, separately compare the byte size of equivalent release artifacts (for example, `.app` and any delivered archive/image) built with matching release conditions. Tauri’s architecture and size documentation explain why a native-webview packaging hypothesis is plausible, but they provide no substitute for this measurement.

## Original conclusion — superseded by the reassessment below

A Tauri 2/Wry wrapper exposes the core macOS-shell primitives, including template tray icons. Local window and monitor capture through `getDisplayMedia()` succeeded in the [native probe](screen-sharing-probe.md); no custom capture bridge was needed. Yandex authentication/calls, complete proxy behavior, and analytics-filter equivalence remain unproven. Public native Apple APIs offer proxy and content-blocking integration points that still require validation. RAM and artifact-size goals remain unmeasured.

## Full-parity architecture reassessment — 2026-09-22

### Decision and evidence boundary

The user retained **full functional parity** and rejected restricted proxy profiles after the native reproduction. No engine change, dependency installation, or new runtime experiment is authorized by this research. The existing Rust/Tauri implementation and bundle remain intact. macOS 26+, Apple Silicon, personal local builds, project-local tools, and user-controlled login/OS consent remain fixed.

The current loopback CONNECT adapter loses the distinction needed to implement Chromium's HTTPS/WSS proxy precedence. With `https=http://127.0.0.1:51213;socks=http://127.0.0.1:51214`, both requests reached the first fixture. Chromium specifies that WebSockets prefer the nonempty “other proxies” list, then HTTPS, then HTTP. This rejects the current adapter as a full-parity solution; it does **not** establish that every WebKit integration is impossible. The adapter also lacks NTLM/Negotiate. [✓ native reproduction in the implementation spec; [Chromium proxy design](https://raw.githubusercontent.com/chromium/chromium/main/net/docs/proxy.md)]

The following findings are source-backed, not runtime acceptance. WebKit `main`, CEF `master`, and cef-rs `dev` are moving sources, not proof of the installed macOS implementation or an approved dependency pin.

### WebKit: public configuration versus private PAC integration

| Path | Source evidence | Parity boundary |
|---|---|---|
| Public `WKWebsiteDataStore.proxyConfigurations` | Per-store proxy configurations, credentials, domain matching/exclusion exist. | No documented original-scheme selection or PAC hook was found. More domain-match tests do not supply the missing same-host HTTPS/WSS selector. Do not repeat the existing CONNECT experiment as though it were a new solution. |
| App-owned `URLSession` / CFNetwork PAC evaluator | An app-owned session accepts `connectionProxyDictionary`; PAC evaluation accepts URL input. | No public API was found that replaces all WKWebView networking with that session. This does not cover page fetches, service workers, subresources, and WebSockets merely by configuring an unrelated session. |
| Private `_WKWebsiteDataStoreConfiguration.proxyConfiguration` | This is a concrete per-store dictionary hook, not a hypothetical Network-framework SPI. WebKit copies the dictionary and assigns it to its internal `NSURLSessionConfiguration.connectionProxyDictionary`. | Candidate for native PAC decisions **before** CONNECT information loss. Installed selectors, PAC URL scheme handling, authentication, bypass equivalence, session persistence, and profile activation at next startup remain untested. |
| `WKURLSchemeHandler` / `NSURLProtocol` | The public WebKit scheme handler is for schemes WebKit does not handle; no public per-store NSURLProtocol hook was found. | Not a demonstrated interception path for ordinary `http`/`https`/`ws`/`wss`. URL rewriting, JS network monkeypatches, and TLS interception are not accepted substitutes. |

Public references: [ProxyConfiguration](https://developer.apple.com/documentation/network/proxyconfiguration), [WKWebsiteDataStore.proxyConfigurations](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/proxyconfigurations-cdc1), [URLSessionConfiguration.connectionProxyDictionary](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/connectionproxydictionary), [WKURLSchemeHandler](https://developer.apple.com/documentation/webkit/wkurlschemehandler).

The private source chain is explicit:

1. [`_WKWebsiteDataStoreConfiguration.h`](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/API/Cocoa/_WKWebsiteDataStoreConfiguration.h) declares `NSDictionary *proxyConfiguration`, annotated macOS 10.15.4+.
2. [`_WKWebsiteDataStoreConfiguration.mm`](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/API/Cocoa/_WKWebsiteDataStoreConfiguration.mm), `setProxyConfiguration:`, copies it into WebKit configuration.
3. [`WKWebsiteDataStorePrivate.h`](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/UIProcess/API/Cocoa/WKWebsiteDataStorePrivate.h) declares `_initWithConfiguration:`.
4. [`NetworkSessionCocoa.mm`](https://raw.githubusercontent.com/WebKit/WebKit/main/Source/WebKit/NetworkProcess/cocoa/NetworkSessionCocoa.mm) assigns `parameters.proxyConfiguration` to the internal session's `connectionProxyDictionary`.
5. Apple's [CFNetwork dictionary constants](https://developer.apple.com/documentation/cfnetwork/global-proxy-settings-constants) include PAC enable/JavaScript/URL, exception patterns, and exclude-simple-hostnames.

This establishes an integration seam, **not PAC/WSS parity**. WebKit passes a WebSocket request to `NSURLSessionWebSocketTask`; Foundation may still normalize the URL before PAC evaluation. Public source inspected here does not settle that behavior. Likewise, CFNetwork's exception patterns and simple-host flag are not proof of Chromium bypass equivalence. Private selectors may change with macOS updates; no supported-API stability or entitlement guarantee is claimed.

**Smallest WebKit gate, requiring approval:** a disposable native WKWebView with an isolated data store configured through this private dictionary. Feed it a PAC rule selecting A for HTTPS and B for WSS; request the **same host and port** over both schemes. Two loopback fixtures record the selected endpoint and may reject the tunnel; no Yandex login, TLS interception, system proxy change, or global tool installation is needed. Check selector availability first. If the PAC route cannot distinguish the schemes, stop this branch rather than extending the CONNECT adapter. If it can, full auth/bypass/TLS/profile-switching validation remains mandatory before integration.

### Rust-hosted CEF: credible alternative, not a Tauri switch

Official CEF supports macOS ARM64. The inspected cef-rs workspace declares `152.4.0+152.0.8`; this is a research snapshot, not an installed or selected release. An experiment must pin bindings, headers, framework, and helper binaries to a compatible exact release. [✓ [CEF build guide](https://github.com/chromiumembedded/cef/blob/master/docs/master_build_quick_start.md), [cef-rs manifest](https://raw.githubusercontent.com/tauri-apps/cef-rs/dev/Cargo.toml), [cef-rs repository](https://github.com/tauri-apps/cef-rs)]

|---|---|---|
| YFI-01–05: lifecycle, endpoint/UA, windows, menus, zoom, unread/tray | Rust/AppKit shell; CEF browser, load/display handlers; existing settings and policy logic where independent of Tauri. | Instance forwarding, AppKit/CEF close sequencing, exact zoom behavior, network and JS user agent, native menu/tray behavior. |
| YFI-06: navigation and popups | `OnBeforeBrowse`, `OnOpenURLFromTab`, `OnBeforePopup`; AppKit external-browser handoff. | Source-policy equivalence, authentication redirects, controlled popup lifetime. |
| YFI-07: camera/microphone and screen/window sharing | `CefPermissionHandler`; prefer Chromium-supported display picker behavior. | Desktop permission flags exist, but they do not prove a usable picker or selected-stream delivery. Chrome-style default permission UI differs from Alloy-style denial. Verify monitor and window selection through actual `getDisplayMedia`, then delivery to a peer. |
| YFI-08–09: filtering and CSS | Request/resource handlers can cancel requests; frame/render APIs inject scripts/styles. | Document and iframe exemptions, dynamic toggles, site CSP/DOM compatibility. |
| YFI-10: proxy profiles | Chromium-native request-context proxy preferences; `GetAuthCredentials` includes `isProxy`, host, port, realm, scheme. | YFI-11: native boundary | CEF browser/render-process messaging only if needed for approved behavior. | No unrestricted remote-page native IPC; source preload existence does not authorize arbitrary commands. |
| YFI-12: local build and resource goals | Complete CEF framework/helper/resource bundle, local signing and permissions. | Exact bundle layout, clean shutdown, complete artifact size and total attributable process-memory comparison. No savings assumed. |

Primary interfaces: [request handler](https://github.com/chromiumembedded/cef/blob/master/include/cef_request_handler.h), [resource handler](https://github.com/chromiumembedded/cef/blob/master/include/cef_resource_request_handler.h), [request context](https://github.com/chromiumembedded/cef/blob/master/include/cef_request_context.h), [preferences](https://github.com/chromiumembedded/cef/blob/master/include/cef_preference.h), [life-span handler](https://github.com/chromiumembedded/cef/blob/master/include/cef_life_span_handler.h), [display handler](https://github.com/chromiumembedded/cef/blob/master/include/cef_display_handler.h), [frame API](https://github.com/chromiumembedded/cef/blob/master/include/cef_frame.h), [permission handler](https://github.com/chromiumembedded/cef/blob/master/include/cef_permission_handler.h), [desktop-capture permission flags and settings](https://github.com/chromiumembedded/cef/blob/master/include/internal/cef_types.h).

The defensible candidate is **Rust + AppKit + CEF**, with one owner for NSApplication, windows, and browser lifetime. CEF documents `multi_threaded_message_loop` for Windows/Linux, not macOS; the main-thread or external-pump integration must be validated. Keeping Tauri solely as a native shell is an additional integration hypothesis, not a documented Wry engine-replacement option. [✓ [CEF application API](https://github.com/chromiumembedded/cef/blob/master/include/cef_app.h), [browser-process handler](https://github.com/chromiumembedded/cef/blob/master/include/cef_browser_process_handler.h)]

A native picker is acceptable under the approved consent/selected-stream requirement; Electron's automatic-first-source implementation is not itself the acceptance criterion. However, a separate ScreenCaptureKit picker does not automatically create a WebRTC MediaStream inside CEF. No such bridge is assumed implemented or feasible without its own evidence.

**CEF gate, requiring approval:** download a pinned ARM64 CEF/binding tuple only into project-local storage and create a disposable native probe, without replacing the application. First prove helper startup, the exact HTTPS/WSS routing counterexample, and monitor/window `getDisplayMedia` selection. Then cover persistent state, auth/bypass, filter document exemptions, navigation/popups, and controlled-peer delivery. Real Yandex login/call/share remains user-assisted. A launch or proxy-only pass does not authorize full migration.

### Recommendation and approval boundary

Two paths retain the full-parity requirement:

1. **Probe the private WebKit PAC seam first.** Smaller change and no new engine download; it tests the missing decision point directly. Tradeoff: a successful result still depends on private macOS interfaces and does not settle authentication or all bypass semantics.
2. **Probe Rust/AppKit/CEF instead.** Chromium owns the required proxy semantics, avoiding a second implementation in the adapter. Tradeoff: engine/framework packaging, shell/message-loop integration, media validation, and unmeasured resource costs.

Recommend the bounded private-PAC probe before discarding the system engine, provided the user accepts researching a private-API dependency. If that risk is unacceptable, choose the CEF probe. Neither choice silently approves production integration, weakens parity, or establishes RAM/size savings. Await the user's choice before executing either experiment.
